# Отчет по обработке ADMX в GPUI

## Краткий вывод

В текущей реализации GPUI не отправляет `ADMX` ни по сети, ни в виде экспортируемого `.admx` файла. Программа:

1. читает `.admx` и связанный `.adml` с диска;
2. разбирает их как XML;
3. преобразует XML в внутренние C++-структуры;
4. по этим структурам показывает политику в UI;
5. на выходе записывает уже не `ADMX`, а реестровые данные в формате `.pol`.

Это подтверждается тем, что `AdmxFormat::read(...)` реализован, а `AdmxFormat::write(...)` всегда возвращает `false` ([src/plugins/admx/admxformat.cpp](/home/fad/git/gpui/src/plugins/admx/admxformat.cpp:829), [src/plugins/admx/admxformat.cpp](/home/fad/git/gpui/src/plugins/admx/admxformat.cpp:844)). Аналогично для `ADML`: чтение есть, запись отсутствует ([src/plugins/adml/admlformat.cpp](/home/fad/git/gpui/src/plugins/adml/admlformat.cpp:376), [src/plugins/adml/admlformat.cpp](/home/fad/git/gpui/src/plugins/adml/admlformat.cpp:394)).

## Как программа получает ADMX

Загрузка начинается в `PolicyBundle::loadFolder(...)`: программа открывает каталог, ищет все файлы с расширением `.admx`, а также подкаталог языка для `.adml` ([src/plugins/administrative_templates/bundle/policybundle.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/bundle/policybundle.cpp:91), [src/plugins/administrative_templates/bundle/policybundle.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/bundle/policybundle.cpp:140), [src/plugins/administrative_templates/bundle/policybundle.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/bundle/policybundle.cpp:156)).

Дальше для каждого `.admx` вызывается `loadAdmxAndAdml(...)`, который:

1. читает `.admx` через плагин `admx`;
2. находит соответствующий `.adml`;
3. читает `.adml` через плагин `adml`;
4. объединяет данные из обоих файлов в общую модель политики.

См. [src/plugins/administrative_templates/bundle/policybundle.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/bundle/policybundle.cpp:317).

## В каком формате ADMX принимается

Входной `ADMX` принимается как обычный XML-документ в кодировке UTF-8. Пример тестового файла начинается так:

```xml
<?xml version="1.0" encoding="utf-8"?>
<policyDefinitions
  revision="1.0"
  schemaVersion="1.0"
  xmlns="http://www.microsoft.com/GroupPolicy/PolicyDefinitions">
```

См. [tests/data/example.admx](/home/fad/git/gpui/tests/data/example.admx:1).

Парсинг делается вызовом `GroupPolicy::PolicyDefinitions::policyDefinitions(input, dont_validate)`, то есть поток `std::istream` разбирается XSD/XML-парсером в объектную модель ([src/plugins/admx/admxformat.cpp](/home/fad/git/gpui/src/plugins/admx/admxformat.cpp:829)).

### Основные XML-блоки ADMX

По коду и примеру используются такие секции:

- `policyNamespaces`
- `resources`
- `supportedOn`
- `categories`
- `policies`

Это видно и в тестовом `example.admx`, и в адаптере `XsdPolicyDefinitionsAdapter`, который извлекает именно эти части ([tests/data/example.admx](/home/fad/git/gpui/tests/data/example.admx:2), [src/plugins/admx/admxformat.cpp](/home/fad/git/gpui/src/plugins/admx/admxformat.cpp:613)).

### Формат описания политики

Каждая политика приходит как XML-элемент `<policy ...>`, где важны поля:

- `name`
- `class` (`Machine`, `User`, `Both`)
- `displayName`
- `explainText`
- `key`
- `valueName`
- `presentation`
- `supportedOn`
- `parentCategory`

Эти поля маппятся во внутренний класс `model::admx::Policy` ([src/plugins/admx/admxformat.cpp](/home/fad/git/gpui/src/plugins/admx/admxformat.cpp:161), [src/plugins/administrative_templates/admx/policy.h](/home/fad/git/gpui/src/plugins/administrative_templates/admx/policy.h:41)).

### Формат значений внутри ADMX

Самое важное по формату данных: значения в `ADMX` приходят не как JSON и не как бинарный блок, а как XML-узлы одного из следующих типов:

- `<decimal value="..."/>`
- `<longDecimal value="..."/>`
- `<string>...</string>`
- `<delete/>`

Это видно в `XsdRegistryValueAdapter::create(...)`, где XML преобразуется в типизированные значения:

- `DECIMAL` -> `uint32_t`
- `LONG_DECIMAL` -> `uint64_t`
- `STRING` -> `QString`
- `DELETE` -> специальный маркер удаления

См. [src/plugins/admx/admxformat.cpp](/home/fad/git/gpui/src/plugins/admx/admxformat.cpp:100).

### Формат элементов политики

Внутри `<elements>` программа принимает несколько разных видов параметров политики:

- `boolean`
- `decimal`
- `enum`
- `text`
- `list`
- `longDecimal`
- `multiText`

Они добавляются в `Policy::elements` как набор объектов `PolicyElement` и наследников ([src/plugins/admx/admxformat.cpp](/home/fad/git/gpui/src/plugins/admx/admxformat.cpp:666), [src/plugins/administrative_templates/admx/policy.h](/home/fad/git/gpui/src/plugins/administrative_templates/admx/policy.h:103)).

## В каком формате программа получает ADML

`ADML` тоже читается как XML, но это уже файл ресурсов: строки локализации и описания представления формы политики. Чтение выполняет `AdmlFormat::read(...)` через `policyDefinitionResources(...)` ([src/plugins/adml/admlformat.cpp](/home/fad/git/gpui/src/plugins/adml/admlformat.cpp:376)).

По сути `ADML` поставляет два типа данных:

- строки вида `$(string.NAME)`;
- presentation-описания вида `$(presentation.NAME)`.

Затем `PolicyBundle` подставляет эти данные в политику:

- `findStringById(...)` заменяет ссылки `$(string.xxx)` на человекочитаемый текст;
- `findPresentationById(...)` подтягивает описание UI-элементов.

См. [src/plugins/administrative_templates/bundle/policybundle.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/bundle/policybundle.cpp:218), [src/plugins/administrative_templates/bundle/policybundle.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/bundle/policybundle.cpp:232), [src/plugins/administrative_templates/bundle/policybundle.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/bundle/policybundle.cpp:341), [src/plugins/administrative_templates/bundle/policybundle.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/bundle/policybundle.cpp:419)).

## Во что ADMX преобразуется внутри программы

После чтения XML данные хранятся не в DOM и не в сыром тексте, а во внутренней модели:

- контейнер файла: `io::PolicyDefinitionsFile`
- набор описаний: `std::vector<std::shared_ptr<PolicyDefinitions>>`
- отдельная политика: `model::admx::Policy`
- элементы политики: `PolicyElement` и наследники

См. [src/io/policydefinitionsfile.h](/home/fad/git/gpui/src/io/policydefinitionsfile.h:40), [src/io/policydefinitionsfile.cpp](/home/fad/git/gpui/src/io/policydefinitionsfile.cpp:35), [src/plugins/administrative_templates/admx/policy.h](/home/fad/git/gpui/src/plugins/administrative_templates/admx/policy.h:41).

Фактически внутренний формат данных выглядит так:

```text
PolicyDefinitions
  -> categories[]
  -> supportedOn
  -> policies[]
       -> name, namespace, key, valueName, policyType
       -> enabledValue / disabledValue
       -> enabledList[] / disabledList[]
       -> elements[]
```

## Что программа “отправляет” дальше вместо ADMX

После редактирования политики GPUI работает уже не с `ADMX`, а с реестровым представлением политики.

Класс `PolicyStateManager` берет `model::admx::Policy` и переносит ее в `AbstractRegistrySource`:

- `DECIMAL` -> `REG_DWORD`
- `LONG_DECIMAL` -> `REG_QWORD`
- `STRING` -> `REG_SZ`
- `DELETE` -> пометка значения на удаление

См. [src/plugins/administrative_templates/registry/policystatemanager.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/registry/policystatemanager.cpp:373).

Если политика отключается, для значений может использоваться специальное имя `**del.<valueName>`, то есть удаление кодируется отдельной строковой записью в реестровом источнике ([src/plugins/administrative_templates/registry/polregistrysource.cpp](/home/fad/git/gpui/src/plugins/administrative_templates/registry/polregistrysource.cpp:138)).

## В каком формате данные сохраняются на выходе

На выходе программа работает с форматом `.pol`, а не `.admx`.

`PolFormat` преобразует внутренние реестровые записи в инструкции вида:

- `key`
- `value`
- `type`
- `data`

С точки зрения типов данных поддерживаются:

- `REG_SZ`
- `REG_EXPAND_SZ`
- `REG_BINARY`
- `REG_MULTI_SZ`
- `REG_DWORD`
- `REG_DWORD_BIG_ENDIAN`
- `REG_QWORD`

См. [src/plugins/pol/polformat.cpp](/home/fad/git/gpui/src/plugins/pol/polformat.cpp:41), [src/plugins/pol/polformat.cpp](/home/fad/git/gpui/src/plugins/pol/polformat.cpp:223), [src/plugins/pol/polformat.cpp](/home/fad/git/gpui/src/plugins/pol/polformat.cpp:248).

То есть выходной формат данных уже такой:

```text
PolicyInstruction {
  key: string,
  value: string,
  type: registry type,
  data: string | uint32_t | uint64_t | string[] | binary
}
```

## Итог

Самое важное:

1. `ADMX` в GPUI только принимается, но не отправляется обратно.
2. Входной формат `ADMX` и `ADML` — XML.
3. Значения из `ADMX` приходят как XML-узлы `decimal`, `longDecimal`, `string`, `delete`.
4. После разбора они превращаются во внутренние C++-структуры `PolicyDefinitions` / `Policy`.
5. На выходе программа формирует не `ADMX`, а реестровые записи и сериализует их в `.pol`.
